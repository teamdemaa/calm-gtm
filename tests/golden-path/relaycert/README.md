# RelayCert golden path

This fixture is the reference acceptance journey for Calm GTM. RelayCert is
fictional. The dates, companies, people, evidence, and outcomes in this folder
exist only to make the product contract concrete and repeatable.

The journey covers:

1. installation and project initialization;
2. a natural, unstructured founder intake;
3. reading supplied material before asking questions;
4. separating facts, hypotheses, and unknowns;
5. asking only material clarifying questions;
6. proposing an APOP strategy without creating a plan;
7. receiving explicit agreement on the APOP strategy;
8. proposing a Now / Next / Later plan without creating assets;
9. receiving explicit agreement on the action plan;
10. approving a short brief for one asset in a separate founder turn;
11. creating only that explicitly approved finished asset;
12. regenerating the local overview;
13. running a five-section weekly check-in without changing strategy on weak
    evidence;
14. creating an optional local HTML view only on explicit request.

## Product under test

RelayCert is a vertical SaaS product for fire-safety maintenance companies
with 5–30 field technicians. It helps the office team catch missing job
documents before they delay certificates and invoices.

## Fixture structure

- `conversation.md` is the canonical conversation.
- `acceptance.md` defines the invariants that implementations must preserve.
- `contract/apop-questions.csv` is the immutable list of 12 strategy questions.
- `fixtures/` contains the supplied materials Calm must read.
- `snapshots/` contains the complete expected `.calm/` state at each gate.

Within every snapshot, `intake.md` contains only the founder's initial context
and material clarifications. Approval state belongs to `strategy.md` and
`action-plan.md`; weekly evidence belongs to `weekly.md`; `sources.md` is the
append-only provenance log for supplied links and documents.

The four stable outputs remain the source models: strategy, action plan,
necessary assets, and weekly check-in. `overview.md` and the optional local
`dashboard.html` are mechanically derived views, never additional decision
systems.

The snapshots are specifications, not files generated by a deterministic LLM
test. Mechanical tests may compare schemas, state transitions, and derived
views. Judgment quality is evaluated against the conversation and acceptance
invariants.
